## DD-R05 — equal-valued die identity is treated as a numerical rule blocker

**Medium; DD-02/24/27/30/34, A02/A05/A18, M2/Q00/E05.**

`src/logic/preparation/d20-configuration.ts:numericD20Roll` (line12) refuses
every non-normal mode. `numericD20ExecutionReason` (line39) makes source-mode
checks unavailable before UI intent can open. `RollModal.tsx` consequently
disables manual advantage/disadvantage. This removes ordinary two-d20 checks,
not just a rare tied result: the block applies before any dice are rolled.

The public harness correctly observes a representation difference. Exact native
`module/dice/basic-die.mjs:BasicDie.advantage` retains the first equal result;
Core `src/server/core/foundry/FoundryDieRules.ts:applyKeepDrop` retains the second
under generic keep/drop. For `[10,10]`, either produces one active10 and one
discarded10. The first/second index can affect which equal die is crossed out in
presentation, but no different numerical rule outcome has been established for
this profile.

The independent fresh run reproduced the unchanged harness exit2 and all40
index differences. A second comparison of its901 results verified:

- Every total and serialized total equals its independently specified value.
- Ordered faces are preserved and all supplied entropy is consumed exactly.
- Exactly one die is active, with the correct selected face value; inactive
  results have consistent discarded flags.
- Every unequal pair retains the exact expected index. All40 differing indices
  occur only when the two faces are equal.
- Results contain only `result`, `active` and optional `discarded`; no distinct
  per-die rule metadata is being lost by considering the equal values equivalent.
- Both complete400-pair distributions match. This is not an inference from a
  few matching totals. The remaining101 cases cover normal numeric inputs and
  source-mode combinations.

See the [portable record](2026-10-19-c06-c07-review.json). The review compared
the original host records; it did not rewrite, reorder or repair runtime rolls.

### Recommended correction and boundary

For this bounded profile, define equivalence using ordered observed faces,
correct selection value/count, discard consistency, numeric outcome and full
distribution. Preserve an equal-value index difference as a nonblocking
diagnostic. The comparison may regard the two identical values as equivalent;
the application must preserve the actual host serialization unchanged.

Restore source/manual advantage/disadvantage through the existing public
primitive once the module's maintained tests encode that boundary and exercise
its preview, shortcut and direct execution paths. Confirm intended manual-mode
choice behavior against the pinned native dialog/configuration semantics; do not
silently drop source modes while removing the block. Keep source changes and
context-loss intent invalidation covered.

Limit this equivalence to homogeneous plain d20 selection with the qualified
numeric bonuses. Do not extrapolate to grouped dice, rerolls, distinguishable
die metadata, effects/flags, range execution, critical annotations or later
die-specific operations. A feature that actually depends on which physical die
was kept needs its own proof and may establish a narrow contract dependency.
No such dependency has been demonstrated for the current plain profile.

The C07 first-tie contract is therefore an unproven external requirement, not
the next mandatory Core task. E05 remains open for broader expressiveness and
unqualified native behavior. E01 remains the confirmed content-discovery
dependency. Do not change Core's generic keep/drop semantics, add another dice
evaluator, rewrite host result records or bump compatibility to solve this case.

The current guards and strict harness were not modified during this review.
The next implementation checkpoint should resolve DD-R05, then continue the
planned independent source-only tool preparation. This is not ADR closeout or
native/operator acceptance.
