## DD-R03 — unavailable profiles leave fabricated card/header numbers

**Medium; DD-01/02/24/34, A02/A03/A18, M2.**

`src/logic/adapter.ts:prepareActorData` only replaces `derived.level` and
`derived.profBonus` when `numericCharacterProfile` returns ready (lines144–145).
Otherwise values from `normalizeActorData` survive: source `details.level` or0,
and source `attributes.prof` or2. `getActorCardData` now prefers those numbers
(lines304–311), even when lifecycle/preparation is unavailable. Header and
proficiency consumers also lack an unavailable state.

Reproduce with `src/tests/fixtures/skill-scenarios.ts:skillSource/skillContext`:
the source has one class with five levels, WIS14 and trained Perception.

| Input | Profile | Card level / proficiency | Skill roll |
| --- | --- | --- | --- |
| Supported baseline | Ready | 5 / +3 | `1d20+5` |
| Each of the three `unavailableContexts()` | Unavailable | 0 / +2 | Refused correctly |
| Add an equipped equipment Item to the baseline | Unavailable pending equipment preparation | 0 / +2 | Refused correctly |
| Change class `system.levels` to `"unknown"` | Unavailable | 0 / +2 | Refused correctly |
| Unsupported context plus source `system.details.level=99`, `system.attributes.prof=99` | Unavailable | 99 / +99 | Refused correctly |

This is a real presentation regression: before C05, the card derived its level
label from class Items; now an unavailable profile makes that same five-level
character display level0. The problem also occurs during the intentionally
unsupported equipment/effect stages, not only malformed input. Source stays
unchanged, and no skill/check/save execution bypass was found.

Correction: make level/proficiency availability explicit and shared by cards,
desktop and mobile. Independently qualified class level may remain known when a
roll-affecting rule is unresolved; otherwise display an unavailable value/reason.
Do not treat a numeric fallback or an old source-derived field as qualification.
Do not fix this by adding a second card calculation or broadening unqualified
rules. Preserve explicit legacy scope separately. Test supported → unavailable →
supported, unresolved equipment/effects, invalid class data and poisoned prepared
fields; include actual header/proficiency/card consumers, not only adapter output.

## DD-R04 — prepared-only proficiency overrides contaminate source fixtures

**Medium; DD-01/02/30/34, A02/A04, M0/M2/Q00.**

At exact native release6.0.6,
`module/data/actor/templates/creature.mjs:CreatureTemplate.defineSchema`
(lines41–63) declares `rolls.ability.{check,save,skill,tool}.proficiency` with
`initial: 0` and `persisted: false`. These are initialized preparation fields,
including effect targets; they are not authorable persisted proficiency overrides.
Native `SchemaField.initialize` selects the field's initial value instead of the
supplied source value for nonpersisted fields.

The new `src/tests/fixtures/ability-scenarios.ts:abilitySource` (lines10–11) puts
these fields directly in source. `src/logic/preparation/abilities.ts` (lines31–35,
41) and `skills.ts` (lines46–53) trust them. The native method harness puts the
same values on an already-initialized plain model, then calls `prepareAbilities`;
that validates arithmetic at a later phase, not how the supplied source reaches
that phase. Three C05 fixture expectations rely on this distinction:
`check-half-and-bonuses`, `int-check-expert`, `con-global-save`.

Reproduce with `abilitySource(abilityCases[1])` (WIS14, class level5). Set a single
global proficiency field; for the save case set persisted WIS proficiency to0.
Leave active effects absent/disabled:

| Injected source field | Module result | Result with native initialization semantics |
| --- | --- | --- |
| `rolls.ability.check.proficiency=2` | Check+8, skill+8 | Check+2, skill+5 |
| `rolls.ability.save.proficiency=1` | Save+5 | Save+2 |
| `rolls.ability.skill.proficiency=2` | Skill+8 | Skill+5 |

A controlled extraction of the local Foundry14.367.0
`common/data/fields.mjs:SchemaField.initialize` confirms all three inputs
initialize to0. The source file SHA-256 is
`efa8e3ccdf553ca826580e60bfbfc97db57bdeadaa954a50f6a55e0ab52c3e01`.
Stubs supply one field entry, the exact declared initial0 and an identity leaf
initializer. This is S evidence, not a running native DataModel/Actor. The
existing exact-native arithmetic comparisons still pass as intermediate-model
comparisons; their count is not proof of source preparation parity.

Ordinary native source should omit these fields. This finding does not claim
all normal characters acquire extra proficiency. It identifies an incorrect
source boundary and a fixture/oracle gap that would conceal later effect-phase
errors or trust stale/prepared data in an input payload.

Correction: initialize nonpersisted fields from verified schema defaults in a
detached preparation model, then apply qualified effects/rules there. Keep
persisted Actor/skill proficiency and persisted roll bonus/mode/range fields
distinct. Until effects are implemented, refuse affected cases as already
planned; do not invent source overrides to simulate them. Separate raw-source
fixtures from deliberately intermediate-model arithmetic fixtures. Add poisoned
nonpersisted-field invariance and supported source/default tests, retaining the
eight independent arithmetic expectations with their correct evidence labels.
Later effect tests must reach these values through the actual module phase
sequence and compare independent native outcomes. No source mutation/migration
or Core extension is needed for this correction.
